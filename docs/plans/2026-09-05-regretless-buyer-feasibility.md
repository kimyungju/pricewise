# 적용 결과

기존 PriceWise 웹검색 서비스에 Planner/Executor 분리, 절대금지·타협가능·중요 프로필, 근거 기반 후회 위험 평가를 적용했다. 사용자가 제공한 세 장의 이미지가 기능 범위다.

## 실행 흐름

사용자 메시지 → Planner → 검색 Executor → 상품·근거 구조화 → 조건 검증·정렬 → 질문 또는 추천 설명

Planner는 action, profile_patch, ask_attribute만 출력한다. 질문 전용 턴에는 검색을 생략한다. 사용자가 타협점을 정하면 기존 근거를 새 프로필로 재평가할 수 있다.

- regret/graph.py: 명시적인 LangGraph 구성. 기존 tools 노드와 승인 interrupt를 유지한다.
- regret/models.py, profile.py: 모델 출력 스키마와 사용자 발화에 근거한 프로필 수정.
- regret/evidence.py: 개별 검색 결과의 URL과 본문 연결, 가격·통화 근거 검사.
- regret/ranking.py: 하드 조건 검사, 우선순위 점수, 후보 간 중요 조건 충돌 탐지.
- regret/nodes.py, prompts.py: 판단 전용 Planner와 조사·설명 Executor.
- api/routes.py: 내부 Planner/조사 텍스트를 고객 토큰 스트림에서 숨긴다. 대화 조회 응답의 regret_profile로 저장 상태를 확인할 수 있다.

## 세 칸의 의미

| 칸 | 저장 예 | 실행 방식 |
|---|---|---|
| 절대금지 (forbidden) | 큰 로고 없음, 장시간 착용 시 통증 없음 | 조건 위반이 확인되거나 충족 여부를 확인할 수 없으면 추천 가능 목록에서 제외 |
| 타협가능 (negotiable) | 날렵한 디자인 | 만족 +1, 불만족 -1, 미확인 -0.5 |
| 중요 (important) | 장시간 편안함 | 만족 +3, 불만족 -3, 미확인 -1.5 |

모든 칸은 사용자가 원하는 조건을 기술한다. matched는 우선순위와 무관하게 사용자 요구 충족을 뜻하고 contradicted는 위반을 뜻한다. 절대금지는 충족이 확인된 경우에만 통과한다. 기존 프로필의 표현 방향이 달라도 source_quote에서 사용자 의도를 해석한다.

예산은 별도 슬롯이다. 명시적 상한은 하드 조건이며, 사용자가 타협 가능하다고 표현한 목표 예산은 초과 비율에 따라 감점한다. 예산·제외 조건을 결과 수 확보 목적으로 자동 완화하지 않는다.

프로필 수정에는 현재 사용자 메시지의 실제 인용이 필요하다. 키 하나를 이동·수정해도 나머지 조건은 남는다. 프로필은 대화 요약문과 별도로 세션 체크포인트에 저장된다. 명시적으로 새 쇼핑 요청을 시작하면 이전 상품 근거의 사용 범위도 분리한다.

## 이미지의 대화가 동작하는 방식

1. 사용자가 편안하고 날렵한 구두를 요청하면 두 속성을 중요한 조건으로 저장하고 검색한다.
2. 후보 A가 편안하지만 투박하고, 후보 B가 날렵하지만 편안함에 반하는 근거를 가지면 중요 조건의 양방향 충돌을 탐지한다.
3. Executor가 어느 쪽의 실패를 더 피하고 싶은지 질문한다. 이 턴에는 Receipt를 만들지 않는다.
4. “디자인은 투박해도 좋아”라는 답변은 디자인을 타협가능으로 옮긴다. 기존 근거를 재평가하면 편안함을 충족하는 후보가 앞서게 된다.

상품 근거가 없으면 시장에 적합한 상품이 없다고 주장하지 않는다. 이미 질문한 속성을 계속 반복하지 않으며, 조사 도구 실행은 턴당 네 묶음으로 제한한다.

## 근거와 보장의 범위

- 후보 URL은 실제 도구 결과에서 가져온다. 상품명과 인용문은 그 URL의 본문에서 확인한다.
- 확인되지 않은 속성은 unknown이다. 출처가 가격이나 명시적 통화를 뒷받침하지 않으면 가격을 미확인으로 처리한다. 달러 기호만으로 USD를 가정하지 않는다.
- 중복된 속성 판정으로 앞선 금지 조건을 덮어쓰는 출력은 스키마 단계에서 거절한다.
- Receipt는 코드가 정렬한 최상위 적격 후보와 검증된 가격에서 만든다. 질문 전용 턴이나 적격 후보가 없는 턴에는 Receipt가 없다.
- 인용문 일치가 의미 해석의 정확성이나 웹페이지의 사실성을 증명하지는 않는다. 편안함·통증·디자인의 의미 판정은 LLM에 의존하고, 주관적 결과를 보장하지 않는다.
- 가중치는 설명 가능한 초기 규칙이며, 실제 후회 확률이나 학습된 개인화 모델이 아니다. 모델 호출 증가에 따른 실제 비용·지연은 별도로 측정해야 한다.
- 기존 채팅 화면으로 질문과 설명이 전달된다. 별도의 세 칸 시각화 UI는 추가하지 않았다.

## 검증

로컬 전체 pytest 126개 통과. 운영 테스트에서 발견한 금지 조건 의미 반전도 수정하고 회귀 테스트 세 개를 추가했다. 실제 gpt-4o 호출에서 확인한 JSON Schema 빈 응답 문제를 피하도록 Planner와 추출기에 function_calling 방식을 명시했으며, SDK 전송 계층 회귀 테스트 두 개를 추가했다. 실제 모델의 인사 요청도 정상 응답했다. 추가한 테스트는 프로필 이동·유지, 하드/유연 예산, 잘못된 가격·통화·출처, 미확인 금지 조건, 중요 조건 충돌, 질문 전용 응답, 세션 격리, 새 요청의 근거 분리, 조사 횟수 제한을 다룬다.

실제 FastAPI 경로와 LangGraph를 사용하는 오프라인 시나리오에서 검색 승인 → 후회 위험 질문 → 우선순위 변경 → 추천 Receipt를 확인했다. 거절 시 검색이 실행되지 않고, 재개 시 Planner가 중복 실행되지 않는 것도 확인했다. 모델 출력과 검색 자료는 고정 fixture이므로, 이 결과는 실제 LLM의 한국어 해석 품질이나 추천 성능 측정은 아니다.

신규 모듈은 Ruff, BasedPyright 오류 검사 및 programming 스킬의 구조 검사로 검증한다. 추천 성능을 정량적으로 평가한 것은 아니다. 운영 환경에서 OpenAI/Tavily 호출, 검색 승인 및 거절, 출처 기반 응답, 가격·통화 미확인 시 Receipt 보류, 프로필 변경·재배포 후 유지까지 확인했다. Vercel 프런트엔드와 Railway 백엔드 자동 배포 및 GitHub CI도 성공했다. 운영 자료에서 검증된 가격을 확보한 Receipt 생성은 아직 확인하지 못했으며, 해당 생성 경로는 오프라인 API 시나리오로 검증했다. 응답 단계에 이번 턴의 실제 도구 결과를 전달하고 내부 조사 완료 문장을 제거해 거절 사유와 사용자 답변의 혼선을 방지한다.

### 기존 대화 호환성 수정

기존 체크포인트의 assistant tool_calls에는 pricewise_internal 표시가 없다. 대화 이력에서 ToolMessage만 제거하면 호출만 남아 OpenAI 400이 발생했다. 공통 대화 투영 함수로 이전 도구 호출도 제외하고, 현재 턴의 실제 호출/결과 묶음은 유지한다. 완료·미완료된 기존 호출을 포함한 SDK 요청 회귀 테스트 네 개를 추가했다. 실제 OpenAI 호출에서 수정 전 messages.[4].role의 400을 재현했고, 동일 이력의 수정 후 요청은 정상 응답했다. 저장된 대화나 프로필은 삭제하지 않는다.

### 누락된 가격 인용 처리

가격 근거가 없는 후보의 price_quote=null을 스키마에서 허용한다. 근거 없는 숫자 가격은 기존 grounding 단계에서 미확인으로 낮추므로 Receipt를 만들거나 필수 예산 조건을 통과하지 못한다. SDK 응답에 후보 세 개의 null 인용을 넣어 기존 오류를 재현했고, 가격 유무·필수 예산 유무를 조합한 네 시나리오를 검증했다. 실제 gpt-4o와 고정 출처 세 개를 사용한 추출에서도 price와 price_quote가 null인 후보 세 개가 정상 파싱됐다.
